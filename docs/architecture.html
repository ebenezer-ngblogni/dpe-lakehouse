Six tâches, une seule bifurcation

Le DAG Airflow tel qu'il tourne réellement : un enchaînement linéaire de six tâches, dont une seule produit deux sorties. Les volumes affichés sont ceux relevés en base.

Pourquoi une seule bifurcation

Le job Spark écrit deux jeux : les lignes retenues et les lignes rejetées. Chaque rejet garde son motif — surface hors bornes, étiquette absente, géocodage non fiable.

Un rejet silencieux est une donnée perdue sans trace. Ici les 720 483 lignes écartées restent interrogeables.

Chaque étape est reprenable

L'ingestion écrit par partition mensuelle, en promotion atomique : un _manifest.json atteste la complétude avant que la partition ne devienne visible.

Le job Spark relit tout le bronze et réécrit le silver en partitionOverwriteMode=dynamic. Le chargement tronque puis recharge. Rejouer le DAG ne duplique rien.

Ce qui reste manuel

L'export vers Power BI n'est pas dans le DAG. Il tourne à la demande, parce que le rapport lit des CSV publiés sur GitHub : l'actualisation dépend d'un git push, pas d'une tâche planifiée.

C'est une limite assumée du montage, pas un oubli — automatiser demanderait un jeton d'écriture dans l'orchestrateur.
